# Контроль производительности запуска

TerraRuntime сохраняет `.wld` каноническим миром, а `.runtime-world` считает одноразовым производным образом для быстрого запуска. Startup gate нужен, чтобы стоимость этих двух путей измерялась по этапам, а не пряталась в одном красивом числе общего времени запуска.

## Что измеряется

Контроль использует два взаимодополняющих источника.

`TerraRuntime.StartupGate` выполняет детерминированный диагностический проход по реальному миру Terraria 1.4.5.8 и печатает одну машиночитаемую строку `startup_gate`. Измеряются:

- чтение канонического файла;
- выделение памяти под тайлы и декодирование тайлов (`wld_tile_reconstruction_ms`);
- декодирование остальных секций `.wld`;
- построение runtime-cache;
- загрузка runtime-cache с проверкой соответствия каноническому источнику;
- изолированная структурная проверка cache (`header + shard table`);
- восстановление тайлов из runtime-cache;
- I/O, hash, decode и restore очереди жидкостей;
- I/O, hash и decode подготовленного runtime-state;
- построение production-контекста кодирования секций и начального bootstrap-cache секций игрока;
- границы холодного и тёплого `WorldReady`;
- суммарные managed allocations и дельты сборок Gen0/Gen1/Gen2 за диагностический проход.

`RuntimeWorldSnapshotProfiler` специально работает вторым диагностическим проходом. Production hot path загрузки cache не обвешивается секундомерами: профилировщик сначала измеряет настоящий loader, а затем повторяет этапы cache изолированно. Поэтому суммарное время worker-операций может быть больше wall time, если shard-чтения выполнялись параллельно.

GitHub Actions workflow `Startup Performance Gate` дополнительно дважды запускает настоящий сервер TerraRuntime на официально сгенерированном мире: без runtime-cache и затем с прогретым cache. Измеряется граница от старта процесса до сообщения о начале прослушивания порта. Это исполняемое доказательство `NetworkReady`.

## Отказы запуска сгенерированного мира

Успешная генерация, атомарная публикация `.wld` и `--worldgen-create-smoke` не доказывают, что TerraRuntime сможет запустить этот мир. При запуске primary сервер затем загружает канонический файл и подготавливает жидкости после загрузки — до допуска cache, подготовки входа игроков и запуска listener. Загрузка официальным TerrariaServer независимо проверяет файл мира, но не проверяет эту границу подготовки TerraRuntime. Приёмка должна также достигать настоящего `NetworkReady` TerraRuntime на сгенерированном файле.

Расследование 2026-09-07 воспроизвело отказ запуска после успешной vanilla-генерации в обоих Windows-профилях поставки. Сохранённые логи содержат `Post-load liquid preparation failed: result=UnsupportedLiquidDeathTile`, а не исключение генератора:

| Мир / профиль | Seed | Первый указанный тайл `(x,y,type)` | Локальный лог проверки |
| --- | --- | --- | --- |
| `Worlds/t.wld`, NativeAOT, Small | `8364953747496893878` | `(220,883,28)` | `artifacts/native-aot/win-x64/logs/runtime-20260907-170322574-75952-0000.jsonl` |
| `Worlds/test.wld`, CoreCLR, Small | `3679097605675226385` | `(359,924,61)` | `artifacts/coreclr/win-x64/logs/runtime-20260907-170408660-81872-0000.jsonl` |
| Изолированное воспроизведение Large, NativeAOT | `8675309` | `(174,1944,12)` | `.cache/tz36-native-win/logs/runtime-20260907-170635386-53780-0000.jsonl` |

Эта диагностика подтверждает fail-closed отказ загрузки на уровне приложения; она не подтверждает нехватку памяти или аварийное завершение процесса средствами ОС/native runtime. Воспроизведение Large завершается той же ошибкой без TUI. Неподдерживаемую семантику уничтожения тайлов жидкостью нужно реализовать и проверить на существующей границе загрузки, а не обходить ради видимого успеха запуска. Эти данные фиксируют исходное воспроизведение, но не означают, что теперь загружается любой seed или мир.

Ранее startup TUI скрывал полезную ошибку: владение терминалом переводило console delivery в буфер, текст прогресса заменял настоящую причину общей фразой о recovery, а финальный framebuffer мог исчезнуть до того, как пользователь его увидит. Теперь startup telemetry сохраняет последнюю ошибку независимо от последующего прогресса, ограничивает её 1024 символами и убирает управляющие символы. При неуспешном запуске причина и код выхода печатаются ровно один раз после освобождения терминала драйвером; если ожидание завершения потока истекло, печать откладывается до фактического освобождения терминала UI-потоком. Нормальный успешный выход и успешное восстановление checkpoint не повторяют старые ошибки, а `--no-tui` сохраняет существующую однократную диагностику в консоли. Искусственная задержка показа, автоматический повтор и альтернативный путь загрузки не добавляются.

## Контракт метрик

Gate сравнительный, а а не жёсткий SLA по миллисекундам. CI проверяет, что все обязательные этапы присутствуют, конечны, неотрицательны и реально выполняются на официальном мире. Абсолютное время зависит от железа GitHub runner, файлового cache ОС и планировщика CPU, поэтому случайно выбранный порог в миллисекундах не должен ломать сборку.

`cache_validation_ms` показывает изолированную стоимость структурной проверки cache. `cache_validated_load_ms` показывает реальное wall-clock время production-загрузки cache с проверкой канонического источника и включает восстановление runtime-state. Нужны обе метрики: первая показывает стоимость validation, вторая показывает фактическую цену тёплого старта.

`index_construction_ms` сейчас включает production-пути `WorldSectionEncodingContext` и `PlayerBootstrapPacketSet.Create`. Эти структуры нужны для кодирования и начальной синхронизации секций игрока. Если появятся новые дорогие индексы, их надо включать в эту фазу или давать им отдельную именованную метрику, а не растворять стоимость в `NetworkReady`.

## Локальный запуск

```bash
dotnet run --project tools/TerraRuntime.StartupGate/TerraRuntime.StartupGate.csproj -c Release -- /path/to/world.wld
```

Команда создаёт `.runtime-world` во временном каталоге и удаляет его после завершения. Канонический `.wld` не заменяется, обычный cache сервера не используется.
