# Серверные часы резервирования и сроки пакетов владельца

В Terraria `1.4.5.8` состояние предмета и пакет `22` имеют разную семантику резервирования. `WorldItem.ReserveFor` меняет назначенного игрока и возраст резерва, затем публикует переданный срок. Этот аргумент не записывается в серверное поле `timeToKeepReservation`. Клиентский обработчик `22` записывает полученное значение в собственное поле.

| Операция | Сохранённые серверные часы | Опубликованный срок |
|---|---|---|
| Обычный `FindOwner` вызывает `ReserveFor` | Сохраняются, обычно `0` | `15` |
| Явный резерв созданного предмета для локального игрока | Сохраняются, обычно `0` | `100` |
| Исходный снимок для подключения | Не изменяются | `0` |
| Положительные серверные часы проходят `UpdateItem` | Уменьшаются на единицу | Нового пакета владельца нет |
| Принудительный поиск владельца | Обнуляются до остальных проверок | Зависит от результата перехода |

`WorldItemSnapshot.TimeToKeepReservation` теперь представляет серверное поле. Существующий `IWorldItemStateCommitSink` получает два необязательных аргумента публикации: `reservationOffer` и `excludedSource`. Они относятся к конкретному событию и не становятся полями сущности или вторым счётчиком. Подготовленный план выделения сохраняет `reservationOffer` с каждой операцией, поэтому немедленное и отложенное принятие публикуют одинаковые пакеты после принятия одинакового серверного состояния. Последующее чтение снимка содержит серверные часы без старого предложения срока.

Общий доверенный API `TryApplyOwner` остаётся явной записью серверного состояния. Выбор владельца и освобождение по правилам vanilla используют `TryApplySourceOwner` с точным исходным снимком: должны совпасть handle, поколение, ревизия и текущее состояние. Операция сохраняет серверные часы, если вызывающая сторона не запрашивает исходное принудительное обнуление, и публикует независимый срок. Клиентский пакет `22` по-прежнему не может записывать авторитетного владельца.

## Поиск, освобождение и подключение

Возраст резерва отделён от поля срока. Исходный сервер увеличивает неотрицательный возраст, ищет владельца неназначенного предмета при остатке `1` от деления возраста на `5` и повторно проверяет активного владельца при остатке `0` от деления на `300`. Запрос смены при активном прежнем владельце отправляет один адресный `39`, устанавливает возраст `-1` и ожидает подтверждения. Принудительный emergency release обнуляет положительный срок обоих участников передачи, включая уже неназначенный предмет; это изменение состояния принимается, даже когда новый `39` или `22` не отправляется. Поиск владельца выполняется до завершения отложенного объединения стопок, поэтому завершение передачи не открывает преждевременный поиск в том же тике.

Подтверждённый запрос `39` сначала освобождает текущего владельца. Принудительный поиск обнуляет серверные часы, обычный сохраняет их. Если предмет остаётся неназначенным, заключительный `22` содержит срок `0` и исключает освобождающее подключение. Новый выбранный владелец получает обычное предложение `15`. Shimmer, задержка подбора для всех игроков и ожидающие передачи сохраняют исходные ограничения выбора. Запросы runtime дополнительно проверяют поколение; сам пакет vanilla `39` не содержит поля поколения.

Производственный код подключения публикует `21` с режимом владения `None`, затем `22` со сроком `0`, как исходные вызовы только с индексом. Он не повторяет режим создания или прежний срок живой публикации. Instanced leases и служебный слот `400` остаются отдельными: payload владельца служебного слота уже является временным предложением для сети, а физический снимок и серверный таймер для него не создаются. Отдельный общий кодек продолжает кодировать явно переданные поля; он не определяет политику подключения.

Последующий живой `21` остаётся отдельным пробелом. Исходный `WorldItem.SyncItem` отправляет режим владения `None` после частичного подбора или объединения. Частичный подбор и emergency transfer в runtime пока сохраняют начальный режим снимка (`ReserveForLocalPlayer = 1`, `GrabDelayForLocalPlayer = 2`), а живой кодек может повторять его; входящий остаток также сравнивается с сохранённым режимом. Поэтому настоящий остаток vanilla с режимом `None` может быть отклонён для такого предмета. Текущий корпус проверяет непосредственное создание и подключение, а сцена отложенного объединения начинается с `None`; он не закрывает переход от ненулевого режима создания к последующему `21`. Сами повторные младшие биты не сбрасывают часы резерва исходного клиента.

Пробник только для разработки отдельно сохраняет исходные серверные поля, возраст и сетевые байты. Захваты используют неизменённый сервер Linux-издания под Windows CoreCLR; они не доказывают Linux NativeAOT или прохождение через GUI. Существующие фикстуры проводки и инструментов не изменены. См.
