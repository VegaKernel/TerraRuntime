# Офлайн-анализ зависимостей исходного кода

`tools/vanilla.py source analyze` собирает отдельный Roslyn probe и составляет перечень зависимостей выбранных оригинальных C#-методов. Он определяет символы, вызовы и представленные обращения к состоянию, чтобы сократить ручной поиск перед адаптацией поведения NPC, генерации мира или игрока. Инструмент не переводит методы, не запускает игру и не доказывает совместимость с Terraria. Поставляемые проекты не ссылаются на анализатор или Roslyn.

Оригинальный `TerrariaServer.exe` `1.4.5.8` и его декомпилированные исходники остаются локальными эталонными входами. Отчёт содержит идентификаторы, диагностики и факты анализа; скопированные тела методов не генерируются. Правило репозитория о самостоятельной реализации по-прежнему действует для production-изменений.

Отдельная экспериментальная операция `source adapt-scalar` теперь **автоматически генерирует** ограниченный кандидат из семантически связанного исходного метода. В отличие от `analyze`, она компилирует кандидата и корректный носитель исходного метода, а затем явно выполняет неизменённую официальную сборку для сравнения. Тела, производные от оригинала, записываются только внутри `.cache` этого worktree; в production-проекты ничего автоматически не включается. У двух операций разные границы приёмки.

[Повторная квалификация main](../verification/semantic-scalar-candidate-main-20261028.json) заново выполняет проверки по настоящему оригиналу в основном checkout. [Общий интеграционный манифест](../verification/ground-critter-semantic-main-union-20261029.json) отделяет доказательства инструмента разработки от приёмки NPC runtime и проверяет оба набора исходников после merge.

[Приёмка схемы 2 в main](../verification/semantic-typed-weapon-main-20261029.json) отдельно подтверждает последующую read-only адаптацию расчёта оружия. Подробные наблюдения и сгенерированные тела остаются в локальном кэше.

```mermaid
flowchart LR
    A[Явные исходные файлы и закреплённые зависимости] --> B[Семантическая модель Roslyn]
    B --> C[Диагностики и ограниченный перечень зависимостей]
```

## Запрос и команда

Запускайте из корня репозитория с Python и используемым в репозитории .NET SDK. Передайте JSON-запрос с явным списком исходников и точными идентификаторами методов. Например, сохраните следующий запрос в локальном cache и замените два входных пути на свои локальные исходники оригинала и разрешённую сборку Linux-сервера:

```json
{
  "schemaVersion": 1,
  "sourceRoot": "C:/local/Terraria1458/decompiled",
  "assembly": "C:/local/Terraria1458/Linux/TerrariaServer.exe",
  "sources": ["Terraria/Utils.cs"],
  "entries": [
    {
      "path": "Terraria/Utils.cs",
      "type": "Terraria.Utils",
      "method": "GetLerpValue",
      "parameterTypes": ["float", "float", "float", "bool"]
    }
  ],
  "maxDepth": 1,
  "maxMethods": 32
}
```

```powershell
py -3 tools/vanilla.py source analyze --request .cache/source-analysis/request.json --output-dir .cache/source-analysis/run01
```

Для каждого запуска выбирайте новый выходной каталог. Исходники задаются явными относительными `.cs`-путями внутри `sourceRoot`; каждая входная точка должна указывать включённый исходный файл. Неизвестные поля запроса, повторяющиеся пути, выход за корень исходников, некорректные входные точки и неверные ограничения отклоняются. Допускается не более 256 исходников, до $32\,\mathrm{MiB}$ на файл и $128\,\mathrm{MiB}$ суммарно. `maxDepth` принимает значения от `0` до `4`, по умолчанию `1`; `maxMethods` — от `1` до `128`, по умолчанию `32`. Тип, имя метода и типы параметров должны определять ровно один метод; C#-псевдонимы нормализуются по каноническому C#-представлению типов Roslyn.

## Как читать доказательства

Новый каталог сохраняет `request.json`, `input-before.json`, `build.log`, `probe.log`, `observation.json` и `result.json`. Runner закрепляет исходники и reference-входы, а также свежие backend DLL/Roslyn-зависимости до и после анализа. Храните эти артефакты вместе.

`accepted` подтверждает только перечень явно посещённых тел методов: входные точки должны быть однозначными, внутри посещённых методов не должно быть ошибок компилятора, некорректных операций или неразрешённых/динамических вызовов, а обход не должен прерываться ни одним ограничением. Проверки входов и исполняемого backend также должны пройти. Общее количество ошибок компиляции сообщается отдельно; принятие результата не означает, что компилируется весь оригинальный проект.

Разрешённый метод, доступный только как metadata, остаётся непрозрачной границей. Сам по себе он не отклоняет перечень, но устанавливает `sourceClosureComplete=false`; анализатор не считает его чистым и не заявляет его транзитивные эффекты. Изучайте такие границы перед планированием адаптации. Достижение ограничения глубины или количества методов отклоняет принятие полного перечня, а не доказывает безвредность оставшихся зависимостей.

Первый эксперимент показал реальный пример такого различия: у `NPC.HaveDryadDoStardewAnimation` были разрешены вызовы и отсутствовали узлы операций `Invalid`, но одновременно существовали конфликт идентичности NPC между исходниками и metadata и отсутствующая встроенная зависимость `ReLogic`. Ни количество разрешённых вызовов, ни число операций не позволяли принять такую семантическую модель. [Запись эксперимента](../verification/roslyn-feasibility-20261028.json) сохраняет точные границы того раннего результата.

Ошибки компилятора, неразрешённые вызовы и остановки на ограничении обхода зависимостей остаются видимыми вместо подстановки предполагаемых значений. Изменение исходного файла или reference во время запуска нарушает привязку результата к входам.

## Как применять перечень зависимостей

Сопоставляйте перечень с существующими владельцами runtime. Например, обращения к оригинальному `Main.npc` — с хранилищем NPC runtime, создание снарядов — с существующей транзакцией публикации, `StructureMap` — с generation workspace, а `Main.rand`/`genRand` — с разрешённым владельцем RNG. Это вопросы адаптации, а не автоматическая эквивалентность или основание создавать параллельные хранилища состояния.

Начинайте с ограниченного семейства, зависимости которого можно представить явно. Сохраняйте порядок изменений состояния, обращений к RNG и границ публикации в самостоятельной реализации. Затем применяйте существующий дифференциальный процесс для [NPC](npc-source-tools.md), [worldgen](worldgen-source-tools.md) или [gameplay](gameplay-source-tools.md) на совпадающих входах оригинала и runtime. Сравнивайте заявленную проекцию состояния и событий и полный RNG; сохраняйте отрицательный контроль, способный обнаружить нужную ошибку.

Перечень не доказывает связи через alias, цели виртуальных вызовов и делегатов, эффекты статической инициализации, динамический порядок выполнения или полные транзитивные эффекты вне заявленной границы. Успешный анализ не подтверждает адаптацию, не повышает статус parity в roadmap и не измеряет ускорение разработки. Для каждого production-изменения остаются обычные требования к сборке, регрессиям, владению состоянием и NativeAOT.

Для ref-локальных переменных и возвращаемых ссылок, небезопасных указателей, свойств, массивов и неявных протоколов `using`/итератора/await/lock сохраняются явные границы неизвестных эффектов. Поля в deconstruction-присваивании отмечаются как записи. Смещения в исходнике обозначают лексические позиции, а не трассу выполнения.

## Проверка анализатора

```powershell
py -3 -m unittest discover -s tools/ci -p test_vanilla_source_analysis.py
dotnet build tools/vanilla_data/SourceProbe/SourceProbe.csproj -c Release -warnaserror
dotnet tools/vanilla_data/SourceProbe/bin/Release/net11.0/SourceProbe.dll --self-test .cache/source-analysis/checks01.json
```

Сначала создайте родительский каталог cache и выберите новое имя результата. Исполняемые проверки используют самостоятельно написанный синтетический C# и metadata базовой библиотеки; оригинальные файлы игры не нужны. Проверяются перегрузки, рекурсия, формы мутаций, непрозрачные эффекты и настоящие отказы по лимитам и ошибкам. Python-проверки охватывают границы запросов, точную привязку методов и происхождения данных, изменение входов/выходов и сбои backend. Ни один из этих наборов не является проверкой совместимости геймплея.

## Экспериментальная автоматическая адаптация scalar-логики

Это исполняемый прототип для instance `void` helpers с явно сопоставленными изменяемыми полями `int`/`bool` и аргументами `int`/`bool` по значению. Он разрешает точные Roslyn symbols, проверяет весь связанный метод по небольшому списку разрешённых операций и преобразует обращения к полям в генерируемое типизированное состояние, передаваемое по `ref`. Затенённые параметры остаются отдельными символами. Каждое сопоставленное поле должно наблюдаться и записываться; объединение двух исходных полей в одну цель запрещено. Attributes с неявными протоколами, properties, другие receivers, globals, calls, arrays, locals, loops, exceptions, числовые преобразования, ref/in/out аргументы и неизвестные эффекты отклоняются. Одного разрешения metadata-символа недостаточно для права переноса.

Запрос вкладывает обычный analysis request и добавляет точные field mappings и явные случаи сравнения. Нужны `maxDepth=0` и `maxMethods=1`. Замените явно локальные пути примера:

```json
{
  "schemaVersion": 1,
  "analysis": {
    "schemaVersion": 1,
    "sourceRoot": "C:/local/Terraria1458/decompiled",
    "assembly": "C:/local/Terraria1458/Linux/TerrariaServer.exe",
    "sources": ["Terraria/NPC.cs"],
    "entries": [{"path": "Terraria/NPC.cs", "type": "Terraria.NPC",
                 "method": "EncourageDespawn", "parameterTypes": ["int"]}],
    "maxDepth": 0,
    "maxMethods": 1
  },
  "fields": [
    {"symbol": "Terraria.NPC.timeLeft", "target": "RemainingTicks", "type": "int"},
    {"symbol": "Terraria.NPC.despawnEncouraged", "target": "ExpiryRequested", "type": "bool"}
  ],
  "cases": [
    {"state": {"RemainingTicks": 750, "ExpiryRequested": false},
     "arguments": [10], "rngSeed": 1458}
  ]
}
```

```powershell
py -3 tools/vanilla.py source adapt-scalar --request .cache/scalar/request.json --output-dir .cache/scalar/run01
```

Новый cache-каталог также содержит `candidate.cs`, `original-carrier.cs`, их скомпилированную сборку и отдельный скомпилированный mutant удаления записи для каждого поля состояния. Неизменённое исходное тело компилируется только внутри корректного cache-only носителя; компиляция всего исходного NPC-файла не заявляется. Глобальные диагностики NPC-файла показаны отдельно от квалифицированного method span. Оба выходных поля сравниваются с носителем и **настоящим неизменённым официальным методом**, с полными исходными checkpoints RNG: cursor и 56 slots. Каждый контроль удаления записи должен дать отличие состояния; исключения runner не считаются обнаруженными mutants. Входы, backend/Roslyn closure и созданные артефакты закреплены хешами.

[Доказательство прототипа](../verification/semantic-scalar-candidate-20261028.json) квалифицирует автоматическую генерацию настоящих `NPC.EncourageDespawn(int)` и `DiscourageDespawn(int)`: по 1 014 случаев с границами signed int, boolean и тремя seed, каждый набор повторён дважды. Сгенерированный исходник, скомпилированный кандидат и полные наблюдения state/RNG повторяются побайтно. Удаление записи времени даёт 468 отличий; удаление записи флага — 507 для каждого helper. Это два небольших NPC helpers, а не автоматический перенос AI3/AI7 или генерации мира. Измеренного ускорения разработки и нового runtime-допуска здесь нет.

Следующий полезный шаг — выбранная по исходникам группа scalar leaf helpers с явным return/state-контрактом, затем отдельно квалифицированные числовые преобразования и вызовы владельцев API/RNG. Для массивов, aliases, collision и транзакций публикации нужны настоящие владельцы до генерации более крупного AI. Сгенерированные кандидаты остаются материалом для ревью в рамках правила самостоятельной production-реализации.

Проверки только инструмента:

```powershell
py -3 -m unittest discover -s tools/ci -p test_vanilla_scalar_candidate.py
dotnet tools/vanilla_data/SourceProbe/bin/Release/net11.0/SourceProbe.dll --candidate-self-test .cache/scalar/checks01.json
```

## Результаты scalar-методов без изменения акторов: схема 2

`adapt-scalar` также принимает отдельную схему2 для результатов `int`, `bool` и конечных `float`. Правила записи схемы1 сохраняются. Схема2 сопоставляет точные поля собственного экземпляра и поля одного явно указанного class-параметра как входы **только для чтения**. Каждая запись добавляет `receiver` (`this` либо исходное имя параметра) и `access: "readOnly"`; запрос добавляет `returnType`. Все входные значения обязательны. Сгенерированный кандидат получает плоское типизированное состояние по `in`; class-аргумент удаляется только после проверки каждого его использования как разрешённого чтения поля.

Пример формы запроса для `GetWeaponCrit(Terraria.Item)` внутри существующей analysis-оболочки:

```json
{
  "schemaVersion": 2,
  "returnType": "int",
  "fields": [
    {"symbol":"Terraria.Player.meleeCrit","target":"MeleeCrit","type":"int","receiver":"this","access":"readOnly"},
    {"symbol":"Terraria.Player.rangedCrit","target":"RangedCrit","type":"int","receiver":"this","access":"readOnly"},
    {"symbol":"Terraria.Player.magicCrit","target":"MagicCrit","type":"int","receiver":"this","access":"readOnly"},
    {"symbol":"Terraria.Item.melee","target":"Melee","type":"bool","receiver":"sItem","access":"readOnly"},
    {"symbol":"Terraria.Item.ranged","target":"Ranged","type":"bool","receiver":"sItem","access":"readOnly"},
    {"symbol":"Terraria.Item.magic","target":"Magic","type":"bool","receiver":"sItem","access":"readOnly"}
  ],
  "cases": [{"state":{"MeleeCrit":17,"RangedCrit":29,"MagicCrit":41,"Melee":true,"Ranged":true,"Magic":true},
             "arguments":[{"receiver":"sItem"}],"rngSeed":1458}]
}
```

В этом фрагменте опущен обязательный `analysis`: добавьте оболочку из предыдущего примера, выбрав `Terraria/Player.cs`, `Terraria.Player.GetWeaponCrit` и тип параметра `Terraria.Item`. Любой float-вход и результат задаётся uint32-битами вида `{"bits":2147483648}`; здесь это отрицательный ноль. Субнормальные и граничные конечные значения сохраняются. NaN, бесконечность, числовые cast/widening и неконечные результаты в этом режиме отклоняются. Поддерживаются scalar locals, присваивание scalar-параметрам по значению, типизированные возвраты и проверенные по списку операции сложения, вычитания и умножения. Properties, globals, API/RNG calls, arrays, reference aliases, unsafe blocks и запись в поля акторов по-прежнему запрещены.

[Доказательство typed weapon](../verification/semantic-typed-weapon-candidate-20261029.json) связывает автоматически сгенерированные `Player.GetWeaponKnockback` и `GetWeaponCrit` с фактическими вызовами неизменённого официального EXE, корректным скомпилированным носителем тела метода, битами результата, неизменными именованными входами и всеми 56 ячейками RNG. Fingerprint исходных Player/Item охватывает все прямые поля, рекурсивно представленные value types и элементы массивов; прочие references сохраняют identity без утверждения об их транзитивных внутренностях. Автоматические mutants удаления модификатора и перестановки приоритета категорий должны менять результат без ошибок исполнения. Созданные профили флагов Item и отдельные чтения категорий через настоящий `Item.SetDefaults` — явные тестовые входы, а не допуск состояния мира или экипировки.

Production-поведение не меняется. Владельцы glove, knockback-buff, stealth и других входных фактов должны отдельно получить допуск до подключения кандидатов к геймплею. `GetWeaponDamageMultiplier`/`GetWeaponDamage` отложены: замыкание property getters и таблиц классификации пока не разрешено. Сгенерированные исходные тела остаются исключительно в `.cache`.
